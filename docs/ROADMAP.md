# نقشهٔ راهِ پنل حامی (Hami Panel)

منطقِ ترتیب: **اول چیزی که جلوی خرابی را می‌گیرد، بعد چیزی که امکانات اضافه می‌کند.**
هر مرحله باید به‌تنهایی قابلِ استفاده و قابلِ انتشار باشد.

## مرحلهٔ ۰ — پایه (اکنون اینجا هستیم)
- [x] مخزن، مجوزِ GPL-3.0، مستندات
- [x] `internal/link`: تولیدِ لینک برای vless / vmess / trojan / shadowsocks
- [x] تستِ بازگشت برای «نشتِ تنظیمات Reality از اینباندِ دیگر»
- [x] اعتبارسنجیِ اینباندِ نیمه‌پیکربندی‌شده (خرابی باید اینجا فریاد بزند)
- [x] مدلِ داده (اینباند، کلاینت، ترافیک، گره، لاگِ رویداد) + مهاجرت‌ها
- [x] مدیریتِ فرایندِ Xray و تولیدِ کانفیگِ سازگار با لینک‌ها (`internal/xray`, دستورِ `hami gen`)
- [x] آزمونِ زندهٔ همان لحظه — در مرحلهٔ ۱ با `hami canary` انجام شد

**خروجی تا اینجا:** `hami gen` از یک مشخصات، کانفیگِ Xray و لینکِ همان اینباند را
می‌سازد. کلیدِ خصوصی واردِ لینک نمی‌شود و تنظیماتِ اینباندِ دیگر نشت نمی‌کند.
`hami canary` با خودِ همان لینک وصل می‌شود و عبورِ ترافیک را تأیید می‌کند.

## مرحلهٔ ۱ — پایداری (اولویتِ اولِ کاربر)
- [x] **کانِری‌تست:** پنل با خودِ لینک وصل می‌شود و رد شدنِ ترافیک را تأیید می‌کند (`hami canary`؛ VLESS و VLESS+Reality روی 127.0.0.1 با Xray 26.3.27)
- [x] نگهبانِ داخلی: بررسیِ پورت، TLS، صحتِ لینک؛ هشدار؛ اگر پورت بسته باشد یک‌بار از روی همان مشخصات ری‌استارت می‌شود و تنظیماتِ اینباندِ دیگر را کپی نمی‌کند (`hami guard`)
- [x] پین‌کردنِ نسخهٔ هسته + ارتقای مرحله‌ای با بازگشت خودکار (`hami pin` / `hami upgrade`؛ اگر آزمونِ نسخه شکست بخورد باینری قبلی برمی‌گردد. نسخهٔ آزمون‌شده: 26.3.27)
- [x] بک‌آپ/بازیابیِ یک‌دستوری (پایگاه داده + تنظیمات) (`hami backup` / `hami restore`؛ tar.gz شامل panel.db + PIN)
- [x] گزارشِ رویدادها (audit log)؛ `hami audit -db panel.db` و ثبتِ رویداد از guard / canary / backup / restore / upgrade

## مرحلهٔ ۲ — کاربران و اشتراک
